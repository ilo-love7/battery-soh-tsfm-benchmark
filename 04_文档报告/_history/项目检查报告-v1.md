## 一、致命问题（不修则整个基准无效）

### 1.1 主脚本永远在跑随机数，却"看起来成功了" ⛔

`run_benchmark.py` 第 14 行把 `src/` 加入路径——**该目录不存在**（源码在 `01_源代码/`）；
第 222-230 行导入 `models.timesfm_wrapper` 等——**这些文件都不存在**。
结果每次运行都会进入 `except ImportError` 分支，用 `np.random.randn()` 造 100 条假数据，再"评估"出 RMSE/MAE/R² 并写入 `performance_metrics.json`。

> 这是最危险的一类错误：流程"成功"，指标"好看"，但没有任何一次真实推理。
> 实测：项目里没有任何一个文件能加载真实电池数据。

### 1.2 模型名幻觉 ⛔

| README 写的 | 实际 |
|---|---|
| **Chromo**（"Chromo Forecasting"） | **Chronos**（Amazon），pip 包 `chronos-forecasting`；README 给的链接 `amazon.github.io/chromo-forcasting/` 是编造的 |
| **Llama-Moirai**（把两个模型混成一个） | **Lag-Llama**（社区，Llama 架构）与 **Moirai**（Salesforce，uni2ts）是两个独立模型 |
| 模型清单缺 Lag-Llama | 方案 §2 明确要求 4 个模型：TimesFM / Chronos / Lag-Llama / Moirai |

`requirements.txt` 里 `chromo-for-forecasting>=0.1.0`、`un2ts>=0.1.0` **两个包名都不存在**（应为 `chronos-forecasting`、`uni2ts`），`pip install -r` 必然失败。

### 1.3 EOL 指标在 MIT 上必然为空 ⛔（方案层面的漏洞，AI 产出只是照抄）

真实数据核实：MIT 阶段 0 的 `mit_cycles.parquet` **已在 EOL 处截断**——末点容量恰为额定 1.1 Ah 的 80.0–80.3%，`cycle_life`（如 1852）与序列长度（1850）一致。

因此"EOL = SOH 首次 ≤ 80%"这条规则在 MIT 上**永远不触发**（真值序列末点刚好卡在 80%），方案 §5 的"EOL 误差"整列会是空值。
正确做法：MIT 直接使用官方 `cycle_life` 作 EOL 真值（已在代码中落地，见 §四）。

## 二、严重问题（能跑但结果错误）

### 2.1 三个数据加载器全部与真实格式不符

| 函数 | 原实现 | 真实格式（已核实） |
|---|---|---|
| `load_mit_data` | `pickle.load` → `pd.DataFrame(data)` | ① 首选阶段 0 的 `mit_cells.parquet` + `mit_cycles.parquet`（124 行 × 21 列 / 100,501 行 × 10 列）；② `MATR.zip` 内 pkl 是**嵌套 dict**（`cycle_data` 为逐循环 V/I/T 数组），`pd.DataFrame(dict)` 会直接报错 |
| `load_nasa_data` | 读 `{folder}/{cell_id}.csv` | **`.mat` 结构体**：`m['B0005'][0,0]['cycle'][0]` 为 616 个循环结构，放电容量在 `data.Capacity` |
| `load_calce_data` | `pd.read_csv(zip)` | zip 内是**每支电池一个 xlsx**（如 `A1-007-DST-US06-FUDS-0-20120813.xlsx`），需按 Cycle Index 分组取放电容量 |

### 2.2 MIT 划分口径错误

方案与 README 都写"41 train / 40 test"。实际 parquet 的 `split` 列是**三划分**：

| 划分 | 数量 | 对应批次 |
|---|---|---|
| train | 41 | batch 1 |
| test | **43** | batch 2 |
| secondary_test | **40** | batch 3 |

漏掉 batch3 这 40 只，等于白丢一个现成的二次测试集（可用于"MIT 内部 OOD"）。

### 2.3 数据准备要求把 20 GB 数据复制进项目目录

README "将以下数据集复制到指定位置"——MIT 原始数据 7.7 GB + 统一格式 4.9 GB，CALCE 4 GB、NASA 0.3 GB。**D 盘当前只剩 24 GB**，且这些数据已在 `D:\项目\02_数据集` 就位。正确做法：配置里写路径引用，零复制。

### 4.2 加载器实测结果

| 数据集 | 实测 | 与真实情况对照 |
|---|---|---|
| MIT | **124 cells**，循环 148–2237 | ✅ 与阶段 0 一致 |

### 4.3 基线实测（MIT test=43 cells，起点 50%，H=64 递归）

| 基线 | MAE（平滑真值，SOH%）中位 | EOL 命中率 |
|---|---|---|
| naive_last | 5.65 | 0% |
| naive_linear | 4.07 | 0% |
| exp_decay | 4.53 | 0% |
| ARIMA | 未跑（缺 statsmodels，已给出安装提示） | — |

> 三条经典外推基线**全部无法命中 EOL**（早中期衰减慢，线性/指数外推在 horizon 内到不了 80%）——这正是基础模型的机会所在，也是论文里最有说服力的对照。

### 4.4 跨库实测（同一基线 naive_linear）

| 数据集 | cells | MAE 中位 | EOL 情况 |
|---|---|---|---|
| NASA PCoE | 4 | 6.11 SOH% | **EOL 误差 14 循环（n=4，真值可用）** |
| CALCE CS2/CX2 | 18 有效 | 2.34 SOH% | 真值 EOL 不可用（0/18，现有 zip 均为寿命前段，未衰减到 80%） |

> CALCE 的 EOL 为空不是 bug：本库 zip 只包含前若干循环（如 CS2_35 仅 100 循环），
> 天然不到 EOL。论文里 CALCE 只报轨迹指标，EOL 列注明 n=0——这条必须在 limitation 写清楚。

### 4.5 环境脚本的一个坑（已修）

`setup_env.bat` 只要包含**非 ASCII 字节**（哪怕只是中文路径），cmd 就会按 GBK 解析 UTF-8 字节流导致行撕裂（报错 `'orlevel' 不是内部命令` 之类）。最终方案：脚本内容全 ASCII、依赖清单移到项目根（`requirements-core.txt`），实测 2 分 11 秒装完并自检通过。
